Let admin approve, reject or waitlist a registration

A program is an event entry in v2, and its registrations are user_event records. The code has no program flag, only an event type. Application-gated programs land in APPLIED, which the Kadet app already labels "Pending approval". Nothing can move a registration out of it: there is no admin write route, the per-user update route only accepts userId and eventId (the validation pipe strips anything else, including a status), and there is no rejected or waitlisted state, or reason field. Admin can only list registrations today.

Technical solution

WhatWhere
Add rejected and waitlisted states UserEventStatus functions/src/api/events/entities/user-event.entity.ts currently INTERESTED, APPLIED, APPROVED, COMPLETED, DROPPED_OUT. Add REJECTED and WAITLISTED. v2 events have no capacity, so nothing waitlists automatically. WAITLISTED is set by admin only, and a waitlisted registration is promoted by setting APPROVED.
Add the reason field UserEvent entity functions/src/api/events/entities/user-event.entity.ts optional rejectedReason, shown in the admin table
Add an admin-only route to set status Next to getEventRegistrations, with the same guards: both Admin and Program Manager can approve, reject and waitlist functions/src/api/events/events.controller.ts takes userId, eventId, status and optional rejectedReason (only used with REJECTED) in a new DTO. Don't widen UpdateRegistrationDto: its route is user-guarded, so a user could approve themselves.
Persist it New service method calling updateRegistration functions/src/api/events/events.service.ts the repository method already merges whatever it is given and bumps modified, so no repository change
Label the new states in the Kadet app EVENT_STATUS and EVENT_STATUS_LABELS src/utils/events.ts in app-playground an unknown status falls back to its raw name, so unlabelled they would show as REJECTED and WAITLISTED

v3 already has WAITLISTED (statuses are REGISTERED, WAITLISTED, ATTENDED), but sets it automatically when an event is at capacity, and has no admin approve or reject. Decided: this is built in v2, so v3 will need the approve, reject and waitlist work ported later.
